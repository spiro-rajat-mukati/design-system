The next generation of product work happens with an agent in the loop. We built this design system so any AI tool — and any person prompting one — can produce real product surfaces that look and behave like the rest of Kijani.

Why our system is AI-ready by default

01

Tokens are machine-readable JSON

481 design tokens authored in the W3C Design Tokens format. Any agent can parse the file, look up a value, and reference it by name without guessing.

02

Components have TypeScript types

Every prop, variant, and size is declared in .types.ts. Agents get autocomplete and validation the same way a human IDE does — no hallucinated APIs.

03

Declarative component specs

Each component ships with a JSON spec describing its anatomy, variants, and token bindings. Agents read the spec the same way the Figma plugin does — so humans and agents share one source of truth.

04

Documentation is part of the artefact

Each component has an inline .md spec covering anatomy, API, accessibility, and do/don't. Agents read these the same way junior engineers do — and produce work that matches the conventions.

The tools we work with

Three integrations cover most workflows from prompt to production. Pick the one that fits the work.

L

Lovable

Prompt-to-app builder for non-developers.

Lovable's agent generates web app code from natural language. Connect it to this system so the generated components are your components, not generic ones — meaning what your PM prototyped this morning is shippable this afternoon.

Connecting Lovable

  1. Create a Lovable project.
  2. Add the design system as a dependency in your Lovable workspace settings: 
    npm install rajatspiro/design-system
  3. Import the token CSS in main.tsx: 
    import "design-system/src/tokens/primitives.css";
import "design-system/src/tokens/semantics.css";
import "design-system/src/tokens/component-tokens.css";
  4. Prompt Lovable with system component names: "Build a sign-in page using the Kijani Button, Field, and TextInput components." The agent will use them.

C

Claude Code

CLI pair-programmer that reads your codebase.

Claude Code runs inside your repo, reads the structure, and writes code that fits. Because this system documents itself via .md specs and declarative component-specs/*.json files, Claude Code uses the right component with the right props on the first try.

Connecting Claude Code

  1. Install Claude Code globally (one-time): 
    npm install -g @anthropic-ai/claude-code
  2. From any project that consumes the design system, run: 
    cd /path/to/your-app
claude
  3. Reference components by name in your prompts. Claude will look up the spec and use them correctly: "Build a settings form using the Field and TextInput components, with a primary Button at the bottom."
  4. For best results, keep this repo open alongside — Claude can read the source .md specs directly.

A

Antigravity

Agentic IDE that drives editors, terminals, and browsers.

Antigravity coordinates multiple specialized agents — coding, planning, browser-testing — against a single goal. Combined with this system's machine-readable contracts, an Antigravity workflow can implement a full feature, run the Storybook visual diffs, and open a PR without leaving the agent.

Connecting Antigravity

  1. Install Antigravity from antigravity.google.
  2. Open the design system repository (or any consumer app) as the active workspace.
  3. Point the planning agent at src/components/ and src/component-specs/ — both are well-structured directories the agent can enumerate.
  4. Run the Storybook MCP integration so the agent can capture Chromatic snapshots as part of its verification step.

Principles for AI-augmented design systems

A few rules we follow so the system stays useful for agents over time:

  • One source of truth. Tokens authored once, in JSON. Anything else (CSS, TS, Figma Variables) is generated. Agents reading the source get the same answer as agents reading the artefacts.
  • Specs over screenshots. A component is documented by its .md + JSON spec, not by a Figma image. Agents can parse structure; they can't parse intent from pixels.
  • Conventional structure. Predictable folders, predictable file names, predictable variant property names. Agents perform best on systems where naming is uniform across components.
  • Explicit not implicit. Defaults are stated, not inferred. The Button's default size is documented as "md" in the type definition, not left to be discovered from CSS.
  • Tests are part of the system. Storybook stories per variant and Chromatic snapshots give agents a way to verify their work — not just generate it.

What's coming next
